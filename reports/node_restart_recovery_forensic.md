# 2026-10-08 Node producer restart sequence forensic

No writer, Shadow, migration or canonical DB mutation was run for this investigation. At inspection time both `bybit-producer.service` and `bybit-node-producer.service` were inactive/disabled, with no matching producer process. The Node journal shows repeated startup failures with `Ambiguous post-anchor exchange sequence` until the service was stopped. Failed epoch rows were not deleted.

## Evidence

- Operator read-only DB query at 16:11 KST: latest displayed trade ID `944d1e11-80f8-5560-a97b-d14d93a252d0`, `2026-10-08T07:02:54.737Z`, `seq=118887018575`, Sell, price `82668.7`, size `62`. The same 20-row output contains at least 19 distinct trade IDs at `07:02:48.786Z` with identical `seq=118887015567` and different prices/sizes. The query used `ORDER BY exchange_timestamp DESC` only; its within-timestamp display order is **not** evidence of execution order.
- Official public REST capture at `07:16:36Z`: anchor ID/payload matched exactly once; the `07:02:48.786Z / seq=118887015567` group contained 28 distinct IDs. The 1,000-row REST page's oldest timestamp was `06:59:49.122Z`, so it covered the displayed anchor time at that capture. The full 28-row DB membership has not been independently inspected by Codex.
- Earlier public REST capture at `07:12:23Z`: 1,000 rows, 135 `(millisecond,seq)` groups containing more than one ID; largest group had 36 IDs. This independently demonstrates that `seq` is not a per-trade unique ordinal.
- Bybit [public-trade specification](https://bybit-exchange.github.io/docs/v5/websocket/public/trade): one message may contain up to 1024 trades and multiple messages may share a `seq`; trade arrays are sorted by match time. The [recent-trade specification](https://bybit-exchange.github.io/docs/v5/market/recent-trade) identifies `execId`, time and cross-sequence but does not grant UUID lexical ordering semantics.
- Read-only public replay at `07:17:21Z`, using the operator-provided anchor and official REST/WS (not a direct peer DB session): anchor REST match `1`, current REST/WS overlap `1`, WS trades observed `1`, unresolved post-anchor tied groups `109`. First unresolved group was `07:17:07.838Z / seq=118887699341`: 3 REST trades, 0 WS witnessed. The corrected algorithm returned `FAIL: Incomplete same-timestamp/sequence WS ordering witness`; canonical writes `0`.

## Root cause and fix

The old `reconcileRecent` created a set of `timestamp:sequence` keys and threw on the second candidate. Real public data and the operator's DB sample prove that this key identifies a batch, not an individual trade. The fix keeps exact ID/payload/available-sequence parity, verifies the full persisted anchor millisecond group, and accepts a multi-trade tied group only when **all** members were observed on the uninterrupted resumed WS so the WS source order is available. REST order and UUID lexical order are never used to fabricate intra-group order. A group with any REST-only member still fails closed; otherwise a price-changing group could change the canonical candle close on replay. No canonical timestamp or existing DB row is modified.

The direct peer-auth DB+REST+WS replay still requires the administrator's read-only command in [node_restart_recovery_admin.md](node_restart_recovery_admin.md). The public replay above is strong evidence of the current unresolved gap but does not prove full persisted-group membership or production restart safety. `LIVE_READ_ONLY_RESTART_TEST=FAIL` for the observed public replay; `RESTART_SAFETY=NOT_VERIFIED`. A future direct replay may also fail if the 1,000-row REST window moves past the anchor. Do not deploy/start the writer on this evidence alone. Obtain an official ordered historical witness or separately authorize a new live epoch; neither is performed here.
